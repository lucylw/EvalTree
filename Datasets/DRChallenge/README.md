# DRChallenge

A benchmark of hard deep-research questions for evaluating the **drtulu** deep-research
agent. Each instance is a `seed_question` that was iteratively rewritten into a harder
`updated_question` (with an attack `strategy` and a `verification_criterion`), then posed
to the agent and graded.

Building an EvalTree over these questions and overlaying the agent's pass/fail rate per
node surfaces the **research capabilities that reliably stump the agent** (high-failure
nodes).

## Files

```
dataset.json                                  # 268 instances (see fields below)
splits/train-test.json                        # indices 0..267 (all instances)
eval_results/real/drtulu/results.json         # one 0/1 per instance, dataset order (1 = FAILED)
EvalTree/                                      # GENERATED by the pipeline — do not hand-edit
```

### `dataset.json` fields

| field | meaning |
|-------|---------|
| `seed_question` | the original question (pipeline **input**) |
| `updated_question` | the hardened question (pipeline **output**; the one the agent answered) |
| `strategy` | how the question was made harder |
| `verification_criterion` | rubric the answer was graded against |
| `drtulu_verdict` | `"PASSED"` or `"FAILED"` — the drtulu agent's grade |

### `results.json`

A JSON array, one entry per instance **in the same order as `dataset.json`**, using the
accuracy format where **`1` = the agent FAILED** and **`0` = PASSED** (this mirrors each
entry's `drtulu_verdict`). Because 1 = failure, node "FAIL_RATE" in the viewer is the
fraction of instances under a capability node the agent got wrong.

## Prerequisites

```bash
pip install -r requirements.txt          # from the repo root
export ANTHROPIC_API_KEY="sk-ant-..."    # stage 1 (opus) + stage 4 descriptions
export OpenAI_API_KEY="sk-..."           # stage 1 (gpt-4o-mini) + stage 2 embeddings
                                         # NOTE the exact capitalization: OpenAI_API_KEY
```

Both keys are required — the pipeline calls Claude (Anthropic) and gpt-4o-mini + embeddings
(OpenAI). Stages 1 and 2 make one API call per instance (268 each), so a full run costs money.

## Run the pipeline

From the **repo root** (`/Users/lucylw/git/EvalTree`):

```bash
bash EvalTree/run_pipeline.drchallenge.sh
```

This runs end to end over all 268 instances:

| step | what it does |
|------|--------------|
| Stage 1a | annotate each instance with a capability phrase (Claude Opus 4.8) → leaf descriptions |
| Stage 1b | annotate again with gpt-4o-mini → embedding-friendly phrasings |
| Stage 2 | embed the gpt-4o-mini phrases (OpenAI `text-embedding-3-small`) |
| Stage 3 | recursively cluster the embeddings into a capability tree (`.bin`) |
| Stage 4 | write a natural-language description for every tree node (Claude Opus 4.8) → `.json` |
| CI | compute per-node failure rate + confidence intervals from `results.json` |
| Viewer | render a standalone demo HTML with the FAIL_RATE overlay |

Re-running only clears this config's own tree, so other variants (below) are preserved.

## Two tree variants

There are two ways to label the tree; they share the dataset, results, and viewer machinery
and their outputs coexist (filenames encode the leaf-label source, so nothing is overwritten):

| variant | script | leaf labels | stage-1 LLM? |
|---------|--------|-------------|--------------|
| **capability annotation** | `EvalTree/run_pipeline.drchallenge.sh` | an LLM-written capability phrase per instance | yes |
| **strategy** | `EvalTree/run_pipeline.drchallenge.strategy.sh` | the dataset's own `strategy` field (the original reason the question was made harder) | **no** — reused verbatim from `dataset.json` |

The strategy variant skips capability annotation entirely; stages 2–4 (embed → cluster →
summarise internal nodes) are otherwise identical. Internal-node descriptions are still
written by an LLM (`DESCRIPTION_MODEL`, default `gpt-4o-mini`); only the per-leaf annotation
step is removed.

```bash
bash EvalTree/run_pipeline.drchallenge.strategy.sh
```

## View the outputs

**Demo HTML (start here)** — a self-contained page, no server needed. Viewers are named
`viewer-<model>-<leaf-labels>-<description-model>.html`, e.g.:

```
Datasets/DRChallenge/EvalTree/viewers/viewer-drtulu-gpt-4o-mini-gpt-4o-mini.html   # capability annotation
Datasets/DRChallenge/EvalTree/viewers/viewer-drtulu-strategy-gpt-4o-mini.html      # strategy variant
```

Open one directly in a browser (`file://`) or:

```bash
open Datasets/DRChallenge/EvalTree/viewers/viewer-drtulu-strategy-gpt-4o-mini.html   # macOS
```

In the viewer you can:
- switch the metric between **FAIL_RATE** and **PASS_RATE**,
- filter capabilities by keyword,
- expand/collapse by depth, and
- toggle individual dataset instances (leaves). Redder nodes = higher failure rate.

**Other generated artifacts** (`<annotation>` is `gpt-4o-mini` for the capability variant or
`strategy` for the strategy variant):

- Tree (human-readable JSON):
  `Datasets/DRChallenge/EvalTree/stage3-RecursiveClustering/[split=full]_[annotation=<annotation>]_[embedding=text-embedding-3-small]_[max-children=10]_[stage4-CapabilityDescription-model=gpt-4o-mini].json`
- Per-node confidence intervals:
  `Datasets/DRChallenge/eval_results/real/drtulu/EvalTree/TREE=[...]/confidence_interval.json`

## Composition & labels

The 268 instances are drawn from the raw graded runs in
`/Users/lucylw/git/gen_dr_queries/claude_inference/runs/` (`sqa_50_100_explore`,
`sqa_50_100_original`, `test_sqa50`). Each run hardens a seed question over several
attempts and grades the agent's answer (`judgment.verdict`) on every attempt:

- **Failing / selected questions** (indices 0–172): the hardened questions the agent was
  challenged on, with `drtulu_verdict` matched to its attempt's verdict (keyed by the
  originating run so duplicate questions take the verdict from the run they were drawn from).
- **Intermediate passing cases** (indices 173–267): every *other* attempt across the runs
  the agent **PASSED** and that wasn't already included. These were added so the classes are
  roughly balanced (137 FAILED / 131 PASSED, ~51% failure) — a heavily failure-skewed set
  makes per-capability error analysis unreliable.

`results.json` is regenerated directly from the `drtulu_verdict` fields (`FAILED`→1, `PASSED`→0).
